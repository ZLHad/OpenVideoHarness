# 09 · 一张剪辑表开几次 Chrome：量过之后，先不共用

*记录于 2026-10-29 · 状态：只交数字，代码没改；本笔记的 PR 只加了这篇 · [English](en/09-browser-starts.md)*

## 问题

页面工具每打开一个页面，就另起一个无头 Chrome（`tools/film/host.mjs` 的 `openFilm`），画完关掉。剪辑表的页面一多，render、determinism、cues 就要起很多次浏览器。想知道：各起几次，冷启动占了多少时间；要是占得多，就让一张剪辑表的页面共用一个浏览器，每页一个标签页。

## 做法

- 一张测试剪辑表：12 个页面条目，每条 1.5 s，各是一个独立的页面（本地时钟），1920×1080，共 18 s、540 帧。每页每帧画一层渐变、400 个半透明圆和一行字，都只由 t 决定。另有一份 160×90 的（CI 夹具的尺寸）。
- 数次数：`CHROME_PATH` 指向一个替身脚本，它记一笔，再 exec 真的 Chrome。每条命令记启动次数和总耗时。
- 量价钱，各 6 次取中位数：a) `openFilm` 打开页面、画一帧、关掉，也就是现在每页都要走一遍的；b) 只启动、只关闭；c) 在开着的浏览器里新开一个标签页，放进它自己的 browser context，做同样的设置，画同一帧，再关掉。a − c 就是共用之后每页省下的时间。
- 三台机器：本机 M3 Max，Chrome 156；GitHub 的 ubuntu-latest 和 macos-latest，一次 `workflow_dispatch`，跑在临时分支上，跑完就删了。
- CI 这一整套：本机跑一遍 `tools/ci.sh --committed`，用同一个替身脚本，记下每次启动是哪个进程起的。

## 发现

1. **次数**：三台机器上都一样（表 9.1），因为次数取决于代码怎么走，不取决于机器。一张 12 页的剪辑表：
   - render 起 24 次。读每页的长度和数据，12 次，一页一次，一页接一页；画的时候，每个 worker 碰到一页就再起一次。
   - determinism 起 50 次。A、B、C、D 四遍各自把页面一页页打开。B 用的是 A 那一份，可它一次最多开着两页，倒着走一遍，又得一页页重开。
   - cues 12 次，frames 取 6 个时刻 7 次，patch 补一段 2 次，只渲一个页面 1 次。
2. **价钱**（表 9.2）：每页另起一个浏览器，比在开着的浏览器里开一个标签页，本机多 0.37 s，Linux runner 多 0.41 s，macOS runner 多 1.67 s。160×90 的页面，两台 runner 上是 0.33 s 和 1.33 s。
3. **能省多少**：可省的次数乘上 a − c。读数据那一步一页接一页，全算；画的时候 4 个 worker 并行，除以 4（表 9.3）。
   - render：这张 18 s 的测试表，本机约省 5 s，是 20%。换成一支 3 分钟、同样 12 页的片子，只有 2–3%：画帧的时间跟着片长涨，起浏览器的次数不涨。
   - determinism：50 次能减到 3 次（A 和 B 一个，C、D 各一个；C 和 D 本来就要另起浏览器）。本机约省 17 s，是 26%；macOS runner 约省 79 s，是 30%。
   - cues：12 次减到 1 次，本机约省 4 s，是 71%。
4. **CI 这一套省得很少**：一次完整的运行起 321 次浏览器，分在 216 个进程里。其中 165 次在起了不止一次的 60 个进程里，但大多数本来就是每个 worker 一个浏览器（单页面的 render 按 `--workers` 起），determinism 的三个也是有意的。真正多出来的只有 18 次，按 macOS runner 的价钱，两个 shard 加起来约 30 s。
5. **顺带看到**：macOS runner 上的 Chrome 会在跑的中途自己升级，这次从 155.0.8059.40 升到了 156.0.8078.49。块缓存的键里有浏览器的版本，所以升级之后那一遍"块缓存全中"的 render 一块也没中，整张重画，起了 24 次。CI 里测块缓存的那几项，要是两次 render 之间正好赶上升级，也会这样。

## 因此改了什么

- 不改代码。动手前定的线是：真片子要是只快几个百分点，就只记下数字。真片子的 render 只快 2–3%。省得多的是 determinism 和 cues，在一台 Mac 上也就是一次省几秒到十几秒。CI 一个 shard 省十几秒。为了这些，要改所有页面工具共用的 host，让几个页面住进同一个浏览器，然后还得重新证明每一帧仍只由 t 决定，不值得。
- 以后真要做，先做读数据那一步（`tools/film/edit.mjs` 的 `allFacts`）：它不出画面，起的次数等于页数，又是一页接一页地起。再做 `EditFilm`：每个 worker 一个浏览器，每页一个标签页、一个 browser context。两步都要先把 host 的事件监听按 session 分开。现在 host 在浏览器上监听所有 session 的报错，几个页面住进同一个浏览器，报错就会串到别的页面上。

## 还没弄清楚的

- 一个浏览器里同时开着两个标签页时，不在前台的那个会不会被限流。host 每画一帧都要等两次 `requestAnimationFrame`，它要是不来，画面就停住了。无头模式的新旧两种实现可能不一样，这次没试。
- 共用以后块缓存的键怎么写：键里已经有 host.mjs 和 browser.mjs 的哈希，代码一改，所有块都会重画一遍。要不要再记下"这一页是在用过的浏览器里画的"，取决于同一页在新起的浏览器里和在画过别的页面的浏览器里，画出来是不是逐字节相同。这一点没比。
- macOS runner 上 160×90 那一份，render 用 4 个 worker 比用 1 个还慢，468.8 s 对 129.3 s。原因没查。
- CI 那一套的次数是在本机数的。次数取决于代码怎么走，所以按同样的次数估了 macOS runner 上的时间，没有在 runner 上再数一遍。
