开工前读到"规格"为止（`bin/vh know --show "playbook/01-pipeline.md#..规格"`）；后面几节（导演模式、审阅页、审阅台、animatic、look-dev、无人值守、长片、子代理、交付前）到用的那一站再读，`bin/vh know --show "playbook/01-pipeline.md#审阅页"` 只打印一节。

## 总表

下表是 `standard` 档位的做法。`quick` 会省掉人工关卡、独立评审和大部分逐场景自查；`studio` 会加上 look-dev、animatic 和多轮打分。在哪几处停下来给人看不跟档位走，看这支片子的下一步贵不贵（下面的"人工关卡"）。各档位具体做多少，见下面的"努力程度"（`bin/vh effort <档位>` 打印那一档的一列，外加底线）。

## 努力程度：三档各做多少

档位怎么定、谁能降档、任何档位都不降的底线，见 CLAUDE.md 的"努力程度"。同一套流程，按档位决定 agent 自己做多少轮、查多细、评审几次；停下来给人看几次不在这张表里定（quick 除外），见下面的"人工关卡"：

| 旋钮 | `quick` 快出 | `standard` 标准 | `studio` 精品 |
|---|---|---|---|
| 适合 | 一句话直接出片，中途不想看；也适合试方向 | 想在关卡上亲自拍板的正式视频 | 要多轮打磨的发布片、旗舰内容、会被反复看的片子 |
| 人工关卡 | 0 道，直接出片。选 quick 就等于授权跳过关卡，把这一点记进 REVIEW.md；需求有歧义时最多问 1 个问题；人点名要拍板的事照样停（导演模式） | 按片子定，不按档位：立意和初版都停；分镜在片子长于约 90 s、3D 渲染重或要调付费接口时单独停，否则随初版那一页给（下面的"人工关卡"） | 同左；关卡 ① 每张立意卡附一段 10–20 s 草图，有关卡 ② 时附全长 animatic |
| 在哪审 | 不设关卡；导演模式要停的在聊天里问，或用静态审阅页 | 静态审阅页；人想逐条勾选、点评时开审阅台（`bin/vh gate … --desk`） | 审阅台：人在页面里勾选、点评、提交；`bin/vh gate … --wait` 在后台等着，提交就接着做；没有后台唤醒的 agent 退回"人回聊天说一声" |
| 立意 | 想两三个一句话点子（12 第 3 节的四个问题可以帮忙），挑 1 个；写一行理由，再写一行同题视频最常见的做法 | 关卡 ① 给有实际差异的立意卡，每张配一帧画面 | 同左，每张配一段 10–20 s 的草图（look-dev） |
| 风格 | 从立意推出来，可以参考 `styles/` 的预设，写明借了什么 | 写在每张立意卡的"画面"一行（专属，或借一个预设）；选卡就一起定了，人可以在回复里换 | 同左；每张卡的草图就是那种风格的小样，借来的预设人想看时在 E0 补小样 |
| 分镜 | 简表：镜头、时长、reads | 完整 STORYBOARD + 分镜预览图 | 同左 + animatic |
| 自查 | 整片一张联系表、一张按目标屏缩的联系表、前 2 s 的 strip，20 条清单速查一遍 | 新做和改过的场景及交界：联系表、关键动作 strip、局部 crop，按问题取，没动的抽查；20 条清单 | 同左，再加目标屏尺寸测试、循环接缝、无损帧确定性、静默故障扫描 |

| 渲染与交付 | 正式画质 mp4 + 联系表（draft 只用来自查） | 正式画质 mp4 + 联系表 | 同左 + 网页版、GIF、封面，按需出 9:16 |
| draft 版数 | 1–2 版 | 一般 3–5 版 | 不设上限，直到过线（整片评审的轮数另有上限，见"独立评审"一行） |
| subagent | 一般不用，需要时开 1 个（便宜一档的模型） | 按需开少量，整支片子 1–3 个（便宜一档的模型），不按章节铺开 | 可以按章节并行 + 独立评审，按需加作曲 subagent |
| 参考研究 | 只读类型文档 | + 类型文档列的案例 | + 拉片参考（`playbook/07`）、深读 `references/` |
| 大致耗时（30 s 左右的片子） | 10–30 分钟 | 1–2 小时 | 3 小时以上 |
| 推理强度建议 | 中 | 高 | 高；最难的一段或评审可以再升一档，量过有用再升 |

最后一行是给能调推理强度的 agent 的建议（例如 Claude Code 选模型时的 effort 档位），不能调就忽略；新一代模型在"高"以上的收益不均匀，最高档留给时间和 token 都不计的少数情况。`quick` 的做法见 `playbook/quick.md`。

## reads：节奏的计量单位

这个概念来自 ClaudeAnimationBase 的 `ANIMATION_GUIDE.md`，是整个流程里最值得掌握的一条。

一个 read 是观众必须看懂的一条信息。每个镜头按顺序列出它的 reads，每条标出起止时间。每条 read 都需要时间让观众"找到 → 看懂 → 消化"，而且两条重要的 read 不能同时发生。

原文的说法是：reads 就是 timing sheet。镜头的长度由 reads 决定：reads 放不下就把镜头加长或删掉一条 read，不要硬挤。

几条推论：

- **快动作，慢含义**：动作本身可以很快，前提是有预备动作提示观众往哪看；动作之后要留出停顿，让观众理解它意味着什么。
- **先把视线引过去**：观众会看正在动的、亮的、大的，或者角色正在看的东西。重要的 read 出现之前，先把视线引到那个位置。
- **一次只讲一件事**：原因和反应要依次发生，不要叠在一起。

反例：demo 结尾的第一版把 7 个 reads 塞进 1.3 秒，没人看得懂发生了什么；拉到 4 秒后才成立。模型最常犯的错误就是节奏：所有东西一个速度，事件一个压着一个，没有停顿。

## 人工关卡：停在哪

人的判断力最值钱的地方，是在改动还便宜的时候。所以一处值不值得停，看两样：下一步贵不贵（长渲染、花钱、每一帧都带的东西），这个决定是不是只有人能做（立意，靠耳朵挑的声音）。档位管 agent 自己查多细，不决定停几次。`standard` 和 `studio` 的片子按下表停；人还点名要亲自拍板的事，按 CLAUDE.md 的"导演模式"另外停。

| 片子 | 停在哪 | 分镜怎么给人 |
|---|---|---|
| 约 90 秒以内，不调付费接口，渲一遍只要几分钟 | 立意（关卡 ①）、初版（关卡 ③） | 照样在写场景之前写好；随关卡 ③ 那一页给，逐镜默认通过 |
| 长于约 90 秒，或重渲染的 3D，或要调付费接口（生图、生视频、按次计费的配音或作曲） | 立意、分镜（关卡 ②）、初版 | 关卡 ② 单独一页，等人回复 |
| `quick` | 不停 | 简表，随成片交 |

短片不单独停分镜，是因为它的 draft 几分钟就出来，看 draft 和看关键帧差不多便宜；长片、3D 和付费的片子，分镜错了要赔上几小时渲染或真金白银，所以先停。

- **这支片子停哪几处，记在 BRIEF 的 `Stops:` 一行。** `default` 由工具按片子算：片长读 Output 一行，3D 读 Engine 一行（Blender、Three.js、3D），付费读 Budget 一行和花费记录。`bin/vh status <项目>` 的 `stops:` 说算出来的计划和原因。工具只认得这几样；别的"下一步贵"（一遍 draft 要渲十几分钟，每一帧都带的东西还没人看过，要请真人录音），你自己把 2 写进这一行。
- **用户自己定看几次，三种说法就够**："直接出"（不停：没提档位按 `quick`，要 `standard` 或 `studio` 的质量是下面的无人值守模式）、"看方向和初版"（`Stops: 1, 3`）、"每步都看"（`Stops: 1, 2, 3`）。要点名某一件事亲自定、某个检查点也停，才用到导演模式那 12 个名字。
- **第一次停时说清打算在哪几处停。** `bin/vh gate <项目> 1` 打印的消息末尾带着这句话。用户回一句"分镜也给我看看"或"分镜不用单独看"，就照改 `Stops:`（`1, 2, 3` 或 `1, 3`；检查点也写在这一行，`1, E3, 3`），原话记进 REVIEW.md。
- **用户的话已经把立意定了，关卡 ① 就不等。** 他给了完整的 brief（怎么讲、给谁看、多长都说了）、现成的脚本或分镜，没有留给他选的事：不出立意卡，把他给立意的那几句原话记在 REVIEW.md 的关卡 ① 下，"定了"写照 brief 做什么，DECISIONS.md 的 concept 一行写已定；发一条消息，说你照这个会做成什么样、打算在哪几处停，不等回复接着做。只给了题目、立意要你来想的，不算；拿不准就出卡。
- **加停随时可以，减停只认用户本人的话。** 你拿不准，或者这一步对这支片子特别要紧，多停一次不用谁批准：给关卡 ② 出一页，它就是一停。计划里的停只有用户在对话里的原话能拿掉，照下面"授权的无人值守模式"的格式记在那一关下面。片子本身贵而 `Stops:` 一行没写 2，关卡 ② 仍在计划里。
- **工具怎么把关**：计划里有关卡 ② 而没有记录时，`bin/vh gate` 不发关卡 ③ 的页，`bin/vh check` 不放成片（`out/final*` 这一类；draft、片段和 animatic 不查这一条）；关卡 ① 的记录照旧由整片的 `bin/vh render` 和 `bin/vh check` 查，见本节末尾。BRIEF 里没有 `Stops:` 一行的项目（这一行加进模板之前建的）照旧是三道关卡，只查关卡 ①。

每次停默认做一页决定优先的审阅页（见下面的"审阅页"），聊天里只发要人定的事和页面路径；`studio` 默认在审阅台停，人在页面里勾选、点评、提交，agent 在后台等着接着做（见下面的"审阅台"）。三处各交什么：

1. **立意和大纲（关卡 ①）**：先定立意。目的是让人在真不一样的方向里选：立意卡之间要有实际差异（换一张，片子的结构或画面就不一样），每张写明推出的画面和钩子，配一帧画面，选一张卡就把风格方向和钩子一起定了（`12-ideation.md` 第 7 节；MV、手绘、实验片也可以交几段草图代替文字卡）。几张按材料定，通常两三张；只有一个方向站得住时，给它配一个平实的备选，并说为什么。再定给谁看、多长，加大纲：一段一句，让人一眼看出片子怎么走、每段给观众什么，段数跟片子走（十几秒的片子可能只有两段，长片按章）。不确认就往下做，后面几乎所有工作都可能白做；立意定错的代价最大，因为风格、结构、主体都是从它推出来的。
2. **分镜（关卡 ②，计划里有它时）**：逐镜头的画面、reads 和转场，按大纲的段落拆页，每镜一张关键帧，可以是草图或灰盒，一页放人一眼看得过来的镜数（`bin/vh storyboard` 默认一页最多 6 镜）；关键镜头（钩子、转折、结尾）可以给几个机位选项和一句理由（`recipes/shot/`），选定的写进镜头表的 `camera`。人看图比读文字快，改分镜只要几分钟，改代码要几小时。节奏要紧的片子（卡配乐、有旁白、长于约 30 秒），这一关再附一版 animatic，做法见下。还有两样趁便宜放进这一关（或样片）：
   - **前 5 s 的连帧**（`bin/vh frames <项目> --strip 0:5 --fps 6`；还没有页面就放开头几个时刻的关键帧）：旁白定稿以后，开头只能靠画面，只看关键帧看不出那几秒有没有事发生。
   - **每一帧都在的东西**（进度条、字幕样式、字体）带上实拍的样子：这些东西后改一次就是整片重渲。一支 33 分钟的 4K 片子（2026-11）到关卡 ③ 才定进度条，改了两版，1080p、4K 都整片重渲，加上压上传版共约 2 小时；开头也是人看了整片才说缺少亮点。
   不单独停分镜的片子：STORYBOARD 和镜头表照样在写场景之前完成（硬规则 3），只是不为它停。出了 draft 以后，`bin/vh storyboard <项目>` 从 draft 里每镜取一帧，关卡 ③ 的 gate JSON 用 `include` 带上（`bin/vh gate <项目> 3 --init` 的骨架已经写好），逐镜默认通过。别的文档里写"随关卡 ② 给人看"的东西（字幕稿、节奏表、每一帧都在的东西的实拍样子），这类片子也随关卡 ③ 那一页给。
3. **初版（关卡 ③）**：draft 成片加联系表，附 reviewer 的分数和没修好的几处。agent 要主动说出自己最不满意的地方，并给出可选的修法，比等人来挑更高效：有几处写几处，最要紧的排前面，没有就说没有，不凑数。

每一关，人的原话都逐字记进 `REVIEW.md`，往后都算数的要求再抄进它开头的"一直有效的要求"；agent 自己定的事和理由记进 `DECISIONS.md`。关卡改了立意或大纲以后，顺手扫一遍 `DECISIONS.md` 和 `NOTES.md` 素材清单的"上屏说法"：作废的决定整行划掉、注明原因（`~~…~~（关卡 ① 后作废）`），不再用的素材也划掉，免得后面照着旧的做。关卡 ① 的记录工具会查：`standard` 和 `studio` 的项目，`bin/vh render` 渲项目自己的整片（不带 `--range`、`--frames`；`out/` 下面的立意草图、look-dev 页不管）和 `bin/vh check` 之前，`REVIEW.md` 的关卡 ① 下（审阅台写的"审阅台反馈 · 关卡 1"一节也算）要有人的原话和"定了：…"一行，`DECISIONS.md` 的 concept 立意那一行状态要是"已定"；缺哪行，它就拒绝并说补哪一行（`tools/gatecheck.py`）。用户的跳过授权记在案的（下面"授权的无人值守模式"），放行。这是给 agent 的护栏，不是锁。只有用户明确说"不用审、直接出"才能跳过，做法见下面的"授权的无人值守模式"。跳过也不等于不写这些文件：BRIEF 和 STORYBOARD 仍然是后续自查的依据。

### 规格：一开始就定下，有默认值

画幅、分辨率、帧率、时长和"在哪看"在建项目时就定：`bin/vh new` 填好"在哪看"、分辨率和帧率（HyperFrames 类型还有画幅；`--aspect`、`--watch phone|feed|desktop`、`--res 1080p|4k` 可以改）。帧率按下表的默认填，剪辑口播跟素材走，所以留着不填；时长看立意，没定时写一个范围。关卡 ① 的审阅页把它们列在"我替你定了"里（gate JSON 的 `delegated`），人不说话就按默认走。只有需求没说发在哪、而它又会改变画幅或字号下限时（例如一支横屏产品片，没说发 B 站还是抖音），才当成一个问题问；说了平台，就按下面的对应关系定"在哪看"。

| 类型 | 画幅 | 帧率 | 分辨率 | 在哪看（默认） |
|---|---|---|---|---|
| 02 知识短视频 | 1080×1920 | 30 | 1080p | `phone` |
| 03 产品片、05 数据 | 1920×1080 | 30 | 1080p | `desktop` |
| 08 梗 | 1080×1350（`--aspect 4:5`）或 1920×1080 | 30 | 1080p | 1080×1350 是 `phone`；横屏默认 `feed`（主要在 X 这类信息流里看） |
| 01 数学、06 论文 | 1920×1080 | 30 | 1080p | `desktop` |
| 04 MV、07 手绘 | 1920×1080（手绘引擎只有这一种画幅） | 24 或 30 | 1080p（手绘引擎暂不支持 4K） | `desktop` |
| 09 剪辑口播 | 跟素材，多为 1080×1920 | 跟素材（恒定帧率） | 1080p（素材是 4K、方向又和成片一致时可以出 4K；从横屏 4K 裁竖屏最多 1215×2160，只够 1080×1920） | `phone` |
| 10 长讲解 | 1920×1080 | 30 | 1080p（发 B 站、YouTube 可以出 4K） | `desktop` |
| 11 照片回顾 | 1920×1080（竖屏：`bin/vh new recap --aspect 9:16`，片子走 `edit.json`） | 30 | 1080p | 横屏 `feed`，竖屏 `phone` |

- **在哪看**决定字号下限和可读性检查缩到多宽（`03-motion-design.md` §4）。平台对应：竖屏、1:1、4:5、3:4 都是 `phone`（HyperFrames 类型用 `--aspect 4:5` / `3:4` 建项目，只出 1080p）；横屏片发抖音、视频号、小红书、微博、X 这类信息流，是 `feed`；发 B 站、YouTube、官网，是 `desktop`。抖音上 2–5 分钟的横屏知识中视频是个例外：`video-types/02-knowledge-short.md` 的"变体：抖音横屏中视频"默认按 `desktop`，理由写在那里。同一支横屏片既要在电脑上看、又要进手机信息流时，优先另出一个竖版（重新构图），而不是把横屏的字放大到 `feed` 那一档。
- **4K**：用户要，或者精品档的片子要发到 B 站、YouTube 这类有 4K 播放的平台时再用；竖屏一般用不上（YouTube Shorts 最高只播 1080p）。照常按 1080p 写，出片时渲成 4K，BRIEF 的 Resolution 写 `1080p, 4k`。canvas、Three.js 这类自己画像素的代码要处理像素密度，出 4K 前先渲一个 4K draft，用 `bin/vh check <4K 视频> --against <1080p 成片>` 比一遍，再裁帧看锐度（`engines/README.md`"出 4K"）。成本：HyperFrames 渲染时间约 2.5–3.5 倍、文件约 3 倍；Blender 约 4 倍。
- **核对和交付**：`bin/vh check` 拿成片对 BRIEF 的 Output 和 Resolution 两行，尺寸、帧率、时长对不上就失败（BRIEF 改了规格，就先改这两行）；色彩标签也一起查。发布用 x264 CRF 18–19、`-preset slow`、`yuv420p`、BT.709 标签。GitHub release 每个文件不能超过 2 GiB；README 里内嵌的视频每个不超过 10 MB（免费账户）。

### 导演模式：每一站能定什么

计划里的关卡是底线（上面的"人工关卡"）；E0–E5 是导演模式加的检查点：人把某件事设成 `own`，或者说"这一步也停一下"（`stop=E3`），才在那里停。下表按时间顺序排，同一站里也是上游的先定。

| 站 | 在流程里 | 能定的事 | agent 交什么（先图后字） | 选项 | 以后再改 |
|---|---|---|---|---|---|
| 关卡 ① | 阶段 1 | `concept` 立意 | 有实际差异的立意卡（通常两三张）：一句话核心想法、为什么是这份材料、主体、首尾、推出的画面和声音、风险；每张一帧画面，`studio` 每张一段 10–20 s 草图。见 `playbook/12-ideation.md` | 2–3 | 分镜后：很高，等于重做 |
| | | `spec` 规格 | BRIEF 的 Spec 几行（画幅、分辨率、帧率、时长、在哪看），默认值见下面的"规格"；默认列在审阅页的"我替你定了"里，人点名 `spec=own` 时给 2 个方案（例如横屏 1080p 给电脑看，或者另出一个竖版进信息流） | 1–2 | 写场景后：中，换画幅要重排版式 |
| | | `outline` 大纲 | 一段一句，段数跟片子走，加一条时长条，写成 BRIEF 的 Outline 表；段名按内容或阶段起（"按下发送 / 信道编码与调制 / 基站接住"），起承转合这类结构标签最多是段名旁的小标签；骨架和节拍见 `playbook/09-narrative.md` 的"骨架菜单"和"节拍表" | 1 | 分镜后：高 |
| | | `style` 风格 | 默认写在每张立意卡的"画面"一行，选卡就定了；人单独点名 `style=own` 时，选卡之后再出从选中立意推出的画面和 1–2 个可借的预设，在同一时刻的对照图；`studio` 每个候选再真渲一段本片内容的小样 | 2–3 | 写场景后：高 |
| | | `hook` 钩子卡 | 默认写在每张立意卡的"钩子"一行，选卡就定了；人点名 `hook=own` 时，选定立意之后，要发平台的片子出 3 张不同类型的钩子卡，每张配 2 个草拟标题和 1 个封面版式；见 `playbook/10-hooks-and-packaging.md` 的"在关卡 ① 怎么用" | 3 | 低：只动开头一段 |
| E0 样帧 | 阶段 2 | `character` 主角 / 主体 | 设定图（`templates/CHARACTER.md`） | 1–2 | 镜头画完后：高 |
| | | `theme` 主旋律 | 两版 4–8 小节的试听，加谱面图；主题怎么写见 `playbook/11-composition.md` 的"写主题" | 2 | 画面对上拍之后：中 |
| | | `style`，人说不清时 | look-dev：同一段 10–20 s，只改一个变量的 2–3 个变体（见下） | 2–3 | 写场景后：高 |
| E1 脚本 | 阶段 3，分镜之前 | `voice` 配音 | 同几句旁白的两种音色或导演方向，各约 10 s | 2 | 锁时后：高，每句的起止都会变 |
| | | `script` 旁白稿 | `templates/SCRIPT.md`：用选定的配音实测每句时长，写出和目标的差 | 1 | 锁时后：高 |
| | | `hook` 钩子画面（人要亲自定时） | 把选定的钩子卡做成画面：开头几个时刻的帧（例如 0.4 / 1.4 / 2.9 s），写明画面和旁白是不是一起在抓人；拿不准时附 1–2 个备选 | 1–3 | 低：只动开头一段 |
| 关卡 ② | 阶段 3 末；片子短、不单独停分镜时，`storyboard=own` 或 `rhythm=own` 让它成为一停 | `storyboard` 分镜 | 按段拆页，每镜一张关键帧，没把握的标红，逐镜默认通过 | 1 | 写场景后：高 |
| | | `rhythm` 剪辑节奏 | 节奏图（镜头、旁白、配乐三轨，超长的标红）加 animatic | 1 | 锁时后：高 |

| E4 样板章 | 阶段 6 开头（长片） | — | 主 agent 亲手做的第一章：联系表加 10–20 s 片段，当全片的标准，再并行；片子里有几种做法时，改成每种一小段样片（下面的"长片"） | — | — |

| E5 锁画面 | 关卡 ③ 之后 | — | 锁画面，之后只改声音、颜色和收尾；附 `bin/vh qa` 的结果和"请听这 3 处" | — | — |

- 同一站要人定的超过 3 件，先发上游的，其余放下一页；不能因为放不下就替人定。人想一次看更多，也可以放在一页。这个上限保护的是人的注意力；表里别的份量（几张卡、几段、几镜、几处）都跟片子的大小走，不是定额。
- `own` 的事在下游用到它之前停，能等的并进下一道关卡的页面。等回复时只做对每个选项都成立的准备（素材、TTS 草稿），不写场景代码。
- 人定了就照做：有顾虑在页面上说一次、附上代价，不反复争。

### 审阅页

每次停：写 `out/review/gate-<n>.json`（`bin/vh gate <project> <n> --init` 写一份骨架，每个 `{填：…}` 说明那里写什么，填完才放行），运行 `bin/vh gate <project> <n>`。它检查 JSON，出 `out/review/gate-<n>.html`（也存成 `index.html`，图、GIF、mp4 和音频在浏览器里直接看、直接听）并记成这一轮；审阅方式（`LOCAL.md`，没写按上表"在哪审"；人点名的用 `--desk` / `--page` / `--chat`）是审阅台时再起审阅台。聊天里只发它打印的那几行。`<n>` 是关卡 `1` `2` `3` 或检查点 `E0`–`E5`，同一站的第二页加 `b`（`2b`）；页属于哪一站，看文件名。只有一两个纯文字的选择时，直接在聊天里问也行。

图不用手拼，`bin/vh` 有现成的：
- **关卡 ②**：把 STORYBOARD 的镜头表写成 `shots.json`（格式见 `bin/vh storyboard -h`；最没把握的镜头写 `"unsure": "为什么"`；canvas-film 可以不写，没有它时从 `film.html` 读实际的镜头），运行 `bin/vh storyboard <project>` 出每段一页的分镜和总览，同时写好 `out/check/storyboard/review.json`；再运行 `bin/vh rhythm <project>` 出节奏图，超过类型回报间隔的镜头、读不完的字幕标红。gate JSON 里写 `"include": "out/check/storyboard/review.json"`，分段、关键帧、每镜的旁白、没把握的镜头和 animatic 就都带进来了；gate JSON 只写 `summary`、`decisions`，节奏图作为 asset 挂在节奏那个决定下，最后 `bin/vh gate <project> 2`。
- **风格**：`bin/vh style compare a,b,c` 出并排对照（`--frame t` 取各 swatch 的同一时刻）。**封面**：`bin/vh cover-preview <封面>` 出各平台信息流的实际大小和小尺寸可读性。**主旋律**：`bin/vh music … --roll` 出每个声部的谱面和响度曲线，给听不见的一方一张能看的图。

页面从上往下：
1. **要你定的事**（默认 ≤ 3 件）：问题；推荐的选项加一句理由；以后再改要花多少（"现在改：低 · 分镜后改：高"）；怎么回（`H1 / H2 / H3`）。最后是照推荐的整句回复，其余默认通过。
2. **图**：每个决定配图，每张一行说明。选项尽量并排成一张图（钩子几行 × 几帧，封面加信息流大小的缩略图）；声音给试听文件，agent 听不见的地方明说。
3. **选项**：一张小表，每个选项一行，写好处和代价。
4. **分段页**（分镜）：按大纲一段一页（镜头多的段 `bin/vh storyboard` 会拆成几页）：关键帧（各引擎的取帧命令见 `playbook/02-verification.md`）、这一段的 animatic、没把握的镜头标红并写一句为什么。逐镜表默认通过，"默认会这样改"的单独标出；人只写要改的（`S04 改：……`）。分段页不只用在关卡 ②：`studio` 片在关卡 ① 可以只放一页开场段（推荐方案开头 20 s 左右的灰盒），让人对着画面定开场。
5. **附录**（折叠）：reads 时间表、转场、实现方式、出处，凡是不影响拍板的都放这里。

写完问自己：人 3 分钟内能不能看完第一屏并回复？

`out/review/gate-<n>.json` 长这样，路径相对项目目录：

```json
{
  "summary": "24 镜分 6 段；先定主角、主旋律、钩子，约 5 分钟",
  "decisions": [
    {"id": "hook", "question": "前 3 秒用哪个钩子？",
     "options": [{"id": "H1", "label": "反常识数字", "pro": "一句话就是结论", "con": "画面抽象"},
                 {"id": "H2", "label": "冲突画面", "pro": "最抓眼，是真事", "con": "要控制白闪"}],
     "recommend": "H2", "why": "你在关卡 ① 倾向它", "cost": "现在改：低 · 只动 0–11 s", "reply": "H1 / H2"}
  ],
  "assets": [{"path": "out/review/hook-options.png", "caption": "每行一个钩子的开头三帧", "for": "hook"}],
  "least_sure": [{"id": "S02", "note": "白闪 0.1 s 会不会刺眼；默认保留 1 次"}],
  "animatic": "out/animatic.mp4",
  "segments": [
    {"id": "1", "title": "钩子", "t0": 0, "t1": 11, "note": "6 刀，平均 1.8 s",
     "shots": [{"id": "S01", "t0": 0, "t1": 1.6, "frame": "out/check/sb/frame-00.png", "see": "两颗卫星相向飞来",
                "vo": "……", "note": "旁白改成先说结果"}]}
  ],
  "appendix": [{"title": "reads 时间表", "path": "STORYBOARD.md"}]
}
```

- **必填**：`summary`，一句话说这页要你定什么、看完要多久；`decisions`，没有要定的写 `[]`。每个决定要有 `question`、`recommend` 和 `reply`（不写 `reply` 就用选项名拼）。选项的 `id` 别用纯数字，免得和决定的编号混在一起；同一页的几个决定也别共用 `id`（一个用 A / B，另一个用 H1 / H2），人随手回一个"A"才不会有歧义。
- **选填**：`version`（骨架带的 1，不读）、`why`、`cost`，选项的 `label` / `pro` / `con`（文字里的换行照样换行），决定的 `columns`（`pro`、`con` 两列的标题，不写是"好处 / 代价"；关卡 ① 的骨架写"这张卡讲什么 / 风险或代价"）；`decided` 和 `delegated`（都是列表，一项一条）、`not_reviewed`（一句话：这页不审什么）、`title`、`lang`（`zh` / `en`；不写就用 BRIEF 的 `Review language`）、`gate`（和文件名不一致时以文件名为准）。审阅台还认 `listen`、`music`、`film` 三个可选字段（见下面的"审阅台"），这一页不管它们。
- `assets[].for` 写决定或分段的 `id`，图就放在它下面，不写就放进"其他材料"；视频加 `t0` / `t1` 只播一段，加 `poster` 指定封面帧。附录的 `text` 可以放简单的竖线表格（`| a | b |`、`|---|---|`）。写了 `animatic`，每个分段页只播自己那一段，播到段尾就停。
- `least_sure` 写镜头号，那一镜就标红；文字里出现的镜头号会链到那一镜。镜头的 `note` 写"默认会这样改"，照样默认通过，但单独标出来。
- `include`：一个 JSON 文件（或几个的列表），路径相对项目，只补 gate JSON 没写的键，gate JSON 写了的优先；`bin/vh storyboard` 写的 `out/check/storyboard/review.json` 就是给它用的。
- 路径只收项目里的文件和 http(s) 链接。缺推荐、缺文件、`for` 指向不存在的 `id` 时，页面照样生成，但退出码是 1，也不打印聊天消息：先改好。字段形状不对（该是列表的写成了字符串）时退出码是 2，什么都不写。

### 审阅台：在页面里勾选、点评、提交

静态审阅页只能看，回复还得回聊天里打"1 S1"。审阅台（`bin/vh desk`）是一个本地网页：同一份 gate JSON 之外，它把立意和大纲、字幕或旁白稿、分镜（跟着视频走）、声音、事实核对、小样的逐秒点评、决定账本和历史都排出来，每一条都能点"可以 / 要改 / 疑问"、写一句、写"改成"，最后一次提交。agent 在后台等着，人一提交就接着做，不用回聊天。

- **什么时候用**：`LOCAL.md` 没写审阅方式时，`studio` 默认用它，`standard` 默认还是静态审阅页，人想逐条点评时也可以开审阅台；`quick` 不设关卡，导演模式要停的那几处在聊天里问或用静态页。
- **语言**：界面语言取 BRIEF 的 `Review language`（`zh` / `en`），按用户第一句话的语言定，建项目时用 `bin/vh new … --lang en`；这一轮的 gate JSON 写了 `lang` 时以它为准（和静态审阅页同一条规则）；页面右上角也能切换。字幕和项目文档照旧用项目自己的语言。
- **每次停**：在后台运行 `bin/vh gate <project> <n> --wait`（Claude Code 的后台命令，`timeout` 给到上限 7200000 ms；它默认等 7100 s）。它出页、起审阅台（只听 127.0.0.1；已经在跑就用它），先打印聊天消息和审阅台地址：发出去，停下。人一提交它就打印反馈、退出，agent 随之被唤醒；超时以后才提交的，下一次 `bin/vh desk wait <project>` 一启动就交出来。人的原话审阅台已经抄进 `REVIEW.md` 的一节，agent 在下面补"定了 / 改了"（`bin/vh desk feedback <project>` 随时再看）；替人定的事照常记进 `DECISIONS.md`。没标的条目都算通过。
- **没有后台唤醒的 agent**（或者 `wait` 超时了）：人提交后回聊天说一声"看审阅台"，agent 用 `bin/vh desk feedback <project>` 读。页面顶上会写 agent 这会儿有没有在等。服务没起来时，页面把回复复制到剪贴板，人直接贴进聊天。
- **页面读什么**：项目文件本身，每次刷新重读，不另存状态。表格怎么写才排得出来（BRIEF 的 Outline 表、SCRIPT 的字幕或旁白表、NOTES 素材清单、DECISIONS 的划线约定、REVIEW、`shots.json`）、gate JSON 给审阅台加的 `listen`（请你听这几处）、`music`（音轨、节拍表、乐段的名字）、`film`（逐秒点评放哪支视频），以及提交的 JSON 格式，都在 `tools/desk/README.md`。读不出结构的文档不会消失：照原文排版显示在对应的页面和"文档"页里。

### animatic：打磨之前先定节奏

animatic 是整片长度的灰盒预演，属于阶段 3，放进关卡 ② 的审阅页，不是一个新阶段。

- **怎么做**：draft 画质即可。HyperFrames 只能按 composition 的尺寸或它的整数倍渲染，不能缩小，所以直接用 `--quality draft` 出原尺寸；要小文件，渲完再用 ffmpeg 缩。几何块代替真素材，字用最终文案、按最终比例的字号，镜头运动和切点按分镜走。配上真实音频，没有就用占位音频（节拍器、临时配乐、TTS 草稿）。长片最省事的灰盒：`bin/vh edit init` 把 `shots.json` 变成剪辑表，每镜一张灰卡，`bin/vh render` 直接出全长 animatic，之后一镜一镜换上真画面（`engines/EDIT.md`）。
- **看什么**：查节奏和含义，不评审美。每条 read 来不来得及读完？段落之间能接上吗？对照 `STORYBOARD.md` 的段落理解和 reads 表逐镜查。
- **核心段先查**：需要解释或叙事的片子，先从分镜 / animatic 挑最难讲清的 20–40 s（段落更短就用整段），用灰盒关键帧、实际字卡和起止时间查信息怎样接上；无旁白片先串读已有字卡。放进现有关卡 ②；授权无人值守时并入已有自查或代审，不加关卡或评审轮次。`quick` 复用简表和已有联系表，不另做样片。
- **之后**：通过后，animatic 的时间线就是阶段 5–6 的骨架。阶段 4 用实测的配音和配乐回写一次时间，E3 锁定以后，场景代码往里填，时间点不再手改。

### look-dev：意见说不清时，先给变体

人的意见常常是"不够炫酷""感觉不对"，说不出具体要什么。这时不要猜着改全片：

- 挑最能代表全片的一段，10–20 s；
- 只用一个预设变量切出 2–3 个变体，例如 HyperFrames 的 composition 变量 `fx` = A / B / C，渲染时用 `--variables '{"fx":"B"}'` 切换；同一段音频，其他都不变；
- 附一张对照联系表：每行一个变体，每列是同一个时刻；
- 变的是外观时，几个变体别都是同一种底色（一次关卡里人要"换个清新画风"，否掉的正是夜色方案）；
- 人说的是"感觉不对"而不是"不够炫"时，变的那个量可以是风格，甚至立意本身：同一段内容，两三种画法或讲法，不只是特效的强弱；
- 重做一段的风格时，先出 2–3 张静帧给人点头，再做整段；
- 人挑一个方向，再按选中的那档做全片。

变体之间只差一个变量，人挑的是方向，不用描述细节。本仓库介绍片的 v3 就是这样做的：先用 `fx` = A / B / C 渲了一版 22.7 s 的 look-dev（12 s 片中段落加 10.7 s 新做的产品信息图），选定 B 档之后才重构全片。

### 授权的无人值守模式

用户可以授权 agent 跳过关卡、一口气做到成片，比如让它通宵做，第二天早上直接看成片。规则如下：

- **先看档位。** 用户只说"不用审、直接出"、没提档位，就按 `quick` 做：不设关卡、不开 reviewer，交付时照 `quick` 路径卡交。本模式是给要 `standard` 或 `studio` 的质量、又不想中途审的情况（"精品，做完再给我看"）。

- **只认用户本人的原话。** 必须是用户在对话里明确说的；协调者或别的 agent 转述的不算。subagent 收到"直接做完"的转述时，由持有原话的主会话去记录授权。
- **原话逐字记进 `REVIEW.md`**，写在每道被跳过的关卡下，附日期和范围（跳哪几关）。格式见 `templates/REVIEW.md` 文末。
- **独立 reviewer 代审。** 被跳过的关卡由全新上下文的 reviewer 代替人来审：`02-verification.md` 第 5 层的人设，TASTE_CHECKLIST 的 20 条加打分层。每轮的问题和修法记进 `NOTES.md`。上限照旧：整片评审最多 10 轮，同一类问题最多改 5 次；到了上限还没解决的口味问题，随成片交给人。底线条目（TASTE_CHECKLIST 标【底线】的）到了上限还 FAIL，交付物第一行写明"有底线 FAIL，不是可发版本"，不出 final，等人定。
- **交付时说清楚**哪些关卡是代审的；每轮的分数、没修好的几处、立意 / hook / 变化里最低的一项，都随成片交给人。用户看完成片的意见照常记进 `REVIEW.md`，之后回到正常流程。

本仓库的介绍片是一个例子（项目在 `projects/` 下，不入库，这里只描述）：关卡 ① 之后，用户在对话里说"你自己做好 早上9点我希望能看到成片"。关卡 ②③ 由协调者和两轮独立 reviewer 代审，第一轮的结论是"修完才能发"，第二轮是"小修即可发"。REVIEW.md 里记着原话、日期和代审记录。用户看完成片后的意见按正常流程处理，见文末"多轮迭代是常态"的最后一条。

## 长片：用 subagent 并行

每个子代理都要从头读一遍契约和文档，token 成倍地花。平时整支片子开 1–3 个就够（难做的一段、作曲、独立评审），不必每章一个；按章节铺开并行留给 `studio`，或者人点名要。子代理默认用便宜一档的模型（`LOCAL.md` 里指定了就照它），主 agent 留着做第一章和总装。

这是 PDoom（9 个 chapter）和 Functional Emotions（7 个 subagent）实际用过的模式：

1. **主 agent（director）先写三份契约**：`STORYBOARD.md` 和 `ANIMATION_GUIDE.md`（画布、调色板、API、禁止项、安全区），加上共享库。
2. **主 agent 亲手做第一个 chapter**，当作参考样板。Functional Emotions 就是先重做 chapter I，再派其余的。
3. **每个 subagent 负责一个 chapter**，只改自己的文件。发现共享文件有 bug 时报告给主 agent，不自己改。
4. **主 agent 看每个 chapter 的联系表**，写批注退回修改，满意才验收。
5. **每个 chapter 的首尾各 0.5 秒**要和相邻 chapter 对齐：方向、颜色、转场都要衔接上。
6. **几个代理同时干活**：各用一个草稿目录；共享文件（引擎、镜头清单）只由主 agent 改；不必整份拷贝项目。

给 subagent 的指令要自包含。写清楚这几项：chapter 的时间范围、对应分镜段落、要读的契约文件、只许改哪个文件、自查预算、交付时要附上哪些联系表。

**动画词表**：分章之前，除了母题表再列一张动画词表，每种动画归哪一章（生长的树 → 第 3 章，咬合的齿轮 → 第 5 章）。母题重复的是意思，动画只跑一段；同一个意思回来时换一种形态（一张静帧、一句话、一个局部）。各路互相看不见，都会拿手边最顺的那一种：一支 33 分钟的片子（2026-11）分镜的母题表把同一种动画排进了四章，人在三章里分别提了。合片以后给 reviewer 一张跨章的联系表，每章一行，专门找重复的动画。

**样片**：片子里有几种做法（讲道理、动情、宏大的 3D）时，铺开之前每种各做一小段，一段验一种能力。这样比只做一个样板章省事：人的意见一次覆盖几种做法，字被挡、字太多这类全局的问题，在正片开工前就能进分镜。

**磁盘和时间**，按这个量级留。一支 33 分钟的 4K 片子（2026-11，30 fps）：1080p 渲 17 分钟，4K（`--dpr 2`）渲 50 分钟，`deliver` 两遍编码压进 8 GB 要 38 分钟；`out/` 峰值约 62 GB（`versions/` 19 GB、母版 8 GB、上传版 8 GB、`cache/` 10 GB），`audio/work/` 11 GB，磁盘到过 97%。`versions/` 留的是每次替换前的整片，最占地方：4K 开渲前看一眼剩余空间，长片把 `OVH_KEEP_VERSIONS` 设成 1（默认每支留 3 个旧版）；超出的进废纸篓，清空了才腾出空间。

### 人要开几路 session 时

人点名按章开几个 session、在每一路里逐章审的，做法同上，多这几条。一支 33 分钟的片子（2026-11）13 章分 5 路，加配音、真实素材、样片各一路，没有互相覆盖：

1. 主 session 先搭全片灰卡骨架，整片随时能渲（`bin/vh edit init`，或者每镜一张灰卡的页面）。各路把自己的灰卡换成真镜头，镜头 `id` 和时间不动。
2. 每章一个文件。要用别章的东西时先放占位，那一章交了再接上。写一页"怎么做一章"：文件归谁、开工命令、怎么单独查自己那一章。
3. 共用文档和共用库只由一路改（主 session，或者它指定的一路），别的路要改的报给它。
4. 人在各路里逐章审，当场改；合片由主 session 做。
5. 不只一章有的意见，听到就改共用库或共用文档，再通知各路。各路分头改时，人看的预览有先有后，同一条意见会一提再提（那支片子有一条提了六次）。

## 子代理分工：美术、声音设计、研究员

不按章节派时，常见的分法是按活派：配音、配乐和音效、几个重要镜头、发布包，分头交给子代理，主 agent 管时间、共享文件和总装。开几个、任务书怎么写，照上一节；名额不够就派最费时的一两样，其余自己做。各自用的命令查 `bin/vh commands`。

| 角色 | 常派的活 | 交回什么 |
|---|---|---|
| 美术 | 重要镜头、风格小样、封面 | 只改分给它的镜头文件；交这几镜的联系表、关键动作 strip、determinism 的结果；生图用 `bin/vh assets add` 登记 |
| 声音设计 | 配音；配乐和音效（可以拆成两个） | 配音、`timeline.json`、字幕；分轨、混音、`qa` 的结果；只能靠转写和波形判断的地方写明；TTS 的音（加 `--aigc`）和下载的音效、音乐用 `bin/vh assets add` 登记 |
| 研究员 | 事实和出处、真实照片和许可；发布包的文案 | 素材清单，每条写出处、有几个来源；照片用 `bin/vh assets add` 登记；PACKAGING.md 的标题、简介、章节，带数字的注明核实状态，署名用 `bin/vh assets credits` |

- **时间依据先交**：旁白片先要配音和它的 `timeline.json`，音乐片先要曲子和节拍表；镜头、配乐和音效都按它对时（硬规则 2）。
- **给研究员一个检索预算**（例如 30–40 次调用），不然常常一跑一个多小时；只在一个来源或聚合站里出现的数字不进标题。

## 交付前：核对人说过的话

REVIEW.md 逐字记着人说过的话。交付前照着它过一遍，人就不用把同一句话说第二遍；agent 自己觉得"都改了"不算数，要回到成片上对。

1. **列出要核对的**：用户最初的需求原话；REVIEW.md 开头"一直有效的要求"的每一条；各关和各检查点下的原话，包括审阅台提交里标"要改""疑问"的条目；对着样片、小样说的话（那是给成片的意见，不只管那一段样片）。
2. **逐条写一行**：原话（可以截短）→ 做到了、做了一部分或没做到 → 在哪（镜头号、时间点、文件，或哪一次改动）。写进 NOTES.md 的"交付核对"一节。
3. **回到成片上看了再写"做到了"**：取那一帧、读那一句字幕、看那个文件，不凭记忆。要靠耳朵判断的（"音乐小一点""这句读慢一点"）你听不了：写量出来的数（`bin/vh qa` 的响度、词级时间戳），并在交付说明里点名请人听那几秒。
4. **没做到的**：能改就改完再交。改不了或有意没改的，在交付说明里逐条说清为什么，由人定。前后两句话矛盾时以后说的为准，在那一行注明。

三档都做，`quick` 也做：它没有关卡记录，核对最初的需求和 REVIEW.md 里记下的话。这一步不加评审轮次，也不为它多停一次；核对表随交付给人，没做到和只做了一部分的几条放在交付说明的前面。

## 多轮迭代是常态

没有一个优秀案例是一轮做完的：

- **PDoom** 做了两轮：第一轮只给歌词和音频；第二轮提高 effort，要求用 p5 笔刷，每镜都要有趣，而且每镜都要衔接下一镜。
- **Functional Emotions** 第一版是精致的排版歌词视频，被否掉了，理由是"还是歌词视频"。用户第二次要求"要真正的 MV，歌词不是主角"；第三次拿 PDoom 当节奏参考，推动"别让画面静止太久"。
- **mexicat** 的版本也"调了几轮"。
- **本仓库的介绍片**：v2 逐条过了 TASTE_CHECKLIST，也过了两轮独立评审，用户看完仍说"不够炫酷"，还听出音乐有几处像卡住。v3 先修音频、做 look-dev，再重构全片。这也是 TASTE_CHECKLIST 加了打分层的原因。

给用户交付 draft 时，主动说出你自己最不满意的地方，比等用户来挑更高效。
